# Native graph resource-identity hook plan (source-only; capture not authorised)

Updated 25/10/2026. This is a feasibility plan grounded in the tracked harness/tracer source, not a capture, runtime binding result, or proof of proprietary-kernel reads. Do not implement a capture or run a reference probe from this plan alone.

## Question and minimum evidence

The unresolved edge is whether a keyed input resource provided to the feature evaluation can be followed, by explicit object identity rather than guessed address equality, to the resource/mapping represented in a pre-decoder launch parameter. A useful trace must distinguish resource creation, key assignment, copies/transforms, interop registration/import/mapping, and launches; retain order/lifetime and enough call context to associate operations with an evaluation. Record metadata only: no texture/tensor contents, weights, raw pointers, or payload bytes beyond the already-approved launch parameter capture policy. If an API does not expose a direct identity edge, report it missing.

Even a complete call-boundary identity chain establishes declared API relationships and launch arguments, not that an opaque kernel actually reads the object or that its value affects output. That requires separate controlled runtime/data-dependence evidence.

## Grounded source seams

- `vr/evaluation-probe.h::set_resource` calls parameter vtable entry 0 with `(params, key, (unsigned long long)(uintptr_t)value)`; `prepare_eye` supplies the four D3D12 texture objects under Color, Depth, MVec, Output. This exact harness call seam can log the explicit key and object passed, if instrumented in a future authorised harness capture. Do not assume it is the public NGX C++ `Set(ID3D12Resource*)` overload: the call is deliberately typed/cast as the unsigned-long-long entry. The exact interface implementation and compatibility for the deployed add-on must be established before hooking an API/vtable slot by ordinal.
- `prepare_eye` creates D3D12 textures and upload buffers and `upload_texture` issues `CopyTextureRegion` from the placed-footprint upload buffer to the texture. For the current harness, instrumentation at this call site can record stable local IDs for source/destination objects, subresource/footprint and ordering directly. A general caller capture would need a D3D12 command-list interception that records both `D3D12_TEXTURE_COPY_LOCATION::pResource` objects (and relevant subresource/placed-footprint fields), plus `CopyResource`/`CopyBufferRegion` and command-list close/queue execution if those paths are observed. If claiming effective ordering across queues, also record queue identity and fence signal/wait dependencies (including relevant completion); submission order alone does not establish cross-queue execution order. Otherwise limit conclusions to recorded/submitted API relationships, not that a copy completed before a launch. Creation records alone do not show which copy occurred.
- `vr/boundary-probe.h::boundary_hook_committed` and `boundary_hook_placed` intercept resource creation, but `boundary_record_resource` retains descriptors and GPU VA, not stable object IDs or copy/key events. Textures have no useful GPU VA in this harness. Extend only after a concrete plan/authorization; use monotonic process-local IDs mapped internally to object identity, never log raw pointer values. Account for COM lifetime and aliasing heaps.
- `vr/capture/nvapi-trace.c` observes kernel create/launch records and captures bounded parameter-block bytes, but not parameter-object setters or D3D12 resource copies. Its launch slots are tracer sequence indices, not a universal runtime identity. A future join must tie the same evaluation/thread/sequence explicitly and retain uncertainties.

## Proposed staged instrumentation, conditional on approval

1. **Pin the actual parameter ABI first.** Identify the exact parameter interface used by the captured add-on/build from its authorised headers/source or a narrowly scoped runtime interface query. Instrument the actual SetResource call boundary (or documented setter entry point) to emit parameter-set ID, exact key, and a local resource ID assigned to the passed object. Do not infer an ID from an address or assume public NGX overload ordinal matches this harness's vtable.
2. **Track D3D12 resource lineage.** At successful create calls, assign local IDs with resource kind/descriptor and lifetime events. At command-list copy calls, record source/destination IDs and exact subresource/footprint/box metadata; record command-list close and queue execution. For effective cross-queue ordering claims, also record queue identity and fence signal/wait dependencies (including relevant completion); submission order alone is insufficient. Otherwise limit conclusions to recorded/submitted API relationships. Include barriers only if needed to interpret ordering/state, not as identity proof. If the observed work uses other copy/transform APIs, add only the corresponding explicit object-bearing seam.
3. **Observe interop at its actual boundary.** Determine from the installed runtime/API path whether D3D12 objects pass through shared handles, CUDA external memory, CUDA graphics registration, staging, or another mapping. Instrument the applicable registration/import/map/unmap operations to link an existing object ID to a new opaque mapping ID, and record mapping type/array/subresource. Do not assume CUDA pointers are D3D12 pointers, linear, or stable across mappings. If the driver/closed add-on does not expose an object-to-mapping join through authorised hooks, stop and preserve the gap.
4. **Join to launch only where directly observable.** Keep the existing tracer's kernel name/sequence and bounded parameter-block bytes. Add a launch-binding record only if an observed API or documented parameter decoder maps a particular slot/parameter capture to a previously tracked mapping ID. Merely finding a numerically similar pointer, matching dimensions/format, matching plane hash, or seeing a launch after SetResource is insufficient.
5. **Validate metadata and controls before any claim.** Independently reproduce a bounded capture; include negative tests for missing SetResource, swapped object, missing copy, alternate subresource, missing interop registration/map, stale/unmapped mapping, launch without binding, and truncated/reordered events. Redact addresses and payload data. Preserve raw evidence locally/ignored and document tool/build hashes, instrumentation coverage and omitted API paths. Only then assess whether the existing schema can be extended to validate the observed chain; its current fixture is not a capture validator.

## Feasibility verdict / remaining blocker

The tracked source confirms the exact harness-side key→object and upload→texture copy seams, and the existing tracer confirms a launch-parameter observation seam. It does **not** establish that a production/vendor caller follows this harness path, which parameter ABI the deployed add-on uses, what D3D12↔CUDA interop path is used, or a direct mapping-ID→launch-parameter relationship. Current traces therefore cannot close raw-input→slot-1 identity. The public NVIDIA NGX header is not sufficient evidence of the proprietary/community add-on's active interface implementation.

A tracked-source/provenance inventory found no tracked `sl_dlss_nr.h`, `sl_version.h`, Streamline build manifest or Streamline-specific NR API references. Harness keys named `DLSSNR.*` exist, but they are not evidence of a Streamline interface. Outside the additions in this handover documenting the investigation, Streamline appears in historical Proton notes only. Public NVIDIA Streamline material confirms a plugin named `sl.dlss_nr` was added in 2.14.0, but the public repository material located for this investigation does not establish an NR-specific public API/header or Linux support. This is bounded negative evidence, not proof that no separately licensed or installed SDK exists and not a statement that Linux support is impossible. Do not infer ABI or platform support from plugin name, binary metadata, or the older add-on's vtable. The actionable blocker is to obtain authorised, version-matched NR integration headers/documentation and package/build provenance for the actual target, then verify its resource/interop path. Until then, no capture is justified and synthetic event joins must not be produced.

The bounded CPU schema in `native-resource-events.py` currently allows synthetic `resource_create`, `set_resource`, `copy`, `interop_map`, `launch`, and `launch_binding` records. It must not be called a valid end-to-end resource chain: it does not encode command submission/lifetime or prove that an event producer observed the object relationships. No schema changes or captures are made by this plan.
