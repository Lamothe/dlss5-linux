# Native graph reconstruction: next concrete gate

## Current evidence boundary

`NATIVE-GRAPH.md` checks substantial static descriptor construction, export routing and conditional source assignment in one pinned DLL build. It does not establish concrete runtime tensor handles/layouts or launch dataflow for the pre-decoder graph. `native-chain-probe.py` executes a constructed native projection/repack chain with controlled activations and candidate weights; it is not the proprietary runtime's graph. Separately, `NATIVE-VENDOR-COMPARE.md` replays the decoder from captured vendor boundary buffers.

The raw reference planes are byte-validated in `NATIVE-INPUT-LAYOUT.md`, but no checked operation maps them into the decoder-boundary activations. Temporal recurrence/reset remains vendor-side evidence in `TEMPORAL-HISTORY.md`. No native live-input image result exists.

## Available local evidence and its limit

Ignored captures `vr/logs/ladder/s0`, `s98` and `s99` each contain three 62,684,160-byte pool snapshots, resource maps and manifest entries for identical harness-generated 720×720 colour/depth/motion planes. In `evaluation-probe.h`, the harness generates gradients/zero motion, uploads them through mapped upload buffers, and later writes those upload-buffer bytes to the named files; the files are dumps, not inputs loaded by the capture harness. Their local trace files are `vr/logs/capture/nvapi-trace-ladder-s0.log`, `nvapi-trace-ladder-s98.log` and `nvapi-trace-ladder-s99.log`. They pin the respective cuts; slot 99 is the decoder, with an 80-byte parameter block. Cut 98 has a 24-byte later-graph launch block. `NVAPI-ARGS.md` and `NVAPI-BINDINGS.md` give the launch inventory and decoded decoder binding contract.

These captures expose pool snapshots and per-cut launch-boundary blocks (slot 0 at `s0`, slot 98 at `s98`, decoder slot 99 at `s99`), but their 24-record resource maps do **not** join the raw input files to model-arena addresses. The harness-created colour/depth/motion textures are recorded as zero-VA texture resources; the named dump files are captured by mapping separate upload buffers. The tracer logs launch parameter bytes, including GPU-address values, but never dereferences those pointers or captures tensor contents. A matching raw-plane digest across manifests therefore does not identify the input's kernel-readable resource.

## Source audit result (25/10/2026)

The requested source-side audit is complete; it confirms the identity gap rather than closing it. In `evaluation-probe.h`, `prepare_eye()` allocates four D3D12 textures and four upload buffers, maps each upload buffer, writes the synthetic planes, then calls `set_resource()` with the texture pointers under `DLSSNR.Color`, `DLSSNR.Depth`, `DLSSNR.MVec` and `DLSSNR.Output`. `upload_texture()` copies each placed-footprint upload buffer into its paired texture with `CopyTextureRegion`, then transitions the texture for shader use. Thus the host's key→texture and upload→texture relationships are explicit in source for this harness.

They are not joined to the first compute launch's readable inputs by current evidence. `boundary_record_resource()` records texture descriptors but obtains `GetGPUVirtualAddress()` (zero for these textures); `boundary_dump_map()` emits no COM identity, key, upload-buffer identity, or copy event. The s0 resource map records the phase-2 colour/depth/motion textures (indices 8/10/12) with VA zero; the named input dumps are separately written from mapped upload buffers. The launch tracer captures the parameter block bytes and raw call slots, and create records associate a handle with a kernel name, but neither records the NGX SetResource calls nor dereferences/interprets tensor addresses. Consequently, coincident dimensions, format, plane digest, or numeric addresses cannot establish that a launch parameter references one of those textures or identify any subsequent copy/transform. The capture is a harness-generated reference, not evidence about production caller inputs.

This is a concrete instrumentation blocker for the raw-input→slot-1 edge. Do not implement a validator against the present artifacts: they lack the necessary join, so such a validator would merely encode assumptions.

## Next bounded investigation

Do not repeat captured decoder comparison, byte-search opaque pools, launch GPU probes, or add more input-layout scaffolding. Close the remaining host-side identity gap for these harness-generated reference inputs, while keeping their relation to any production/vendor caller inputs explicitly unestablished:

1. The source proves key→D3D texture identity and upload-buffer→texture copy for the synthetic harness only. Existing map/trace formats provide neither resource identity across those APIs nor the object passed to NGX SetResource. A new reference capture would need metadata-only events: stable process-local resource IDs assigned at successful texture/upload creation; key→texture-ID at SetResource; copy-command upload-ID→texture-ID with subresource/footprint/format; and launch name/slot plus the exact parameter-block bytes already captured. Instrument any observed CUDA/D3D interop object and mapping type (which need not be a linear device pointer), plus staging/transform boundaries, to join texture identity to an actual launch argument only if the API directly exposes that relationship; absent such a boundary, retain the gap. Record no tensor contents and make no claim about vendor caller inputs.
2. This requires rebuilding and running the Proton reference harness/tracer with the new metadata, then independently reproducing paired captures and a direct slot-1 launch join (the first input-consuming launch; slot 0 is the clear kernel). Until that safe reference experiment is authorised/available and produces the relation, treat the raw-plane→slot-1 edge as blocked.
3. Only after a concrete producer→consumer edge can be stated should a fail-closed validator be implemented. Require bounds/uniqueness checks, independently reproduced input/capture pairs and synthetic corruptions; keep raw bytes and proprietary payloads local/ignored. Do not use address coincidence or a synthetic replay as a substitute.

## Acceptance distinction

Even a validated edge remains intermediate evidence. End-to-end acceptance still requires raw/live input preprocessing, complete native graph execution and learned-weight bindings, native temporal history/reset recurrence, output conversion, and image comparison against repeated vendor references—all without Windows, DirectX or Proton in the evaluator.
