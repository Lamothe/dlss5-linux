# Native tensor repacking — 09/10/2026

`native-tensor-probe.py` tests two embedded SM89 repacking kernels, **not inference**. The CPU reference is an experimentally validated field/layout interpretation on six shapes, not a fully recovered ABI or an instruction-level proof.

## Evidence and scope

The current-source report `research/native-linux/runs/tensor-execute-FjBfYpkw/output.json` records 24 launches and 48 readbacks on the RTX 4070 Ti SUPER (CUDA driver API 13040): both directions, two distinct bijective word patterns, and shapes `(height, width)` of `(4,4)`, `(4,8)`, `(8,4)`, `(8,8)`, `(12,8)` and `(16,12)`. Each direction is compared independently against the full CPU destination, with the source and surrounding guards checked unchanged. Four shapes expose a non-identity permutation; `(4,4)` and `(8,4)` alone cannot distinguish the two layouts. This is stronger than a GPU round trip but does not independently prove all possible dimensions or field semantics.

The matching `research/native-linux/runs/tensor-skip-repack-nHk2eAD4/output.json` records zero launches, two readbacks, an unchanged poisoned destination and rejection of that destination as successful output. Both reports include the five known-answer pairs, ten directional checks and 19 rejected CPU controls. On 10/10/2026 independent review found no substantive execution/cleanup defect, but identified the previously stale evidence references in this document. The parent independently recomputed all four current-source and retained-snapshot hashes against both manifests; every hash matched. Both runs exited zero with empty stderr. These are verified existing runs, not new GPU execution on 10/10/2026.

SM89 parameter metadata verifies **one opaque 24-byte argument at offset zero**, not four named internal fields. The host packs candidate source/destination 64-bit addresses at offsets 0/8 and candidate height/width signed 32-bit fields at offsets 16/20. Host size/offset assertions validate our own packing only. The full-buffer results above experimentally support that interpretation for these six shapes. They do not recover an authoritative internal ABI, prove arbitrary launch safety, or establish neural model semantics.

## Behavioural derivation and independent known answers

All indices below are zero-based **uint32 word** indices. The logical token is `(y, x)` in row-major order; each token has 512 words, labelled channel pairs without asserting their numerical interpretation. The candidate layout uses 4×4 spatial tiles of 8192 words. In 2D, tile rows are row-major; in 1D, consecutive groups of 16 logical tokens are tiles. The observed within-tile interpretation groups eight channels into 128 words: spatial positions 0–7 advance by 16, positions 8–15 add one, channels 0–3 advance by four, and channels 4–7 add two. Subsequent channel groups add 128.

The literal fixtures are separately enumerated logical-token examples, not outputs generated by `mapping()` or `within_tile()`:

| Shape H×W | Logical token `(y,x)`, channel | 2D tile / spatial / local word | 1D tile / spatial / local word | Known `(2D, 1D)` words |
| --- | --- | --- | --- | --- |
| 4×8 | `(0,4)`, 0 | 1 / 0 / 0 | 0 / 4 / 64 | `(8192, 64)` |
| 4×8 | `(2,1)`, 5 | 0 / 9 / 23 | 1 / 1 / 22 | `(23, 8214)` |
| 8×8 | `(1,4)`, 8 | 1 / 4 / 192 | 0 / 12 / 193 | `(8384, 193)` |
| 12×8 | `(8,5)`, 511 | 5 / 1 / 8094 | 4 / 5 / 8158 | `(49054, 40926)` |
| 16×12 | `(5,9)`, 4 | 5 / 5 / 82 | 4 / 5 / 82 | `(41042, 32850)` |

For example, `(2,1)` at width 8 is logical token 17. In 2D it is spatial position 9 of tile 0; channel 5 contributes `2 + 4`, and position 9 contributes `1 + 16`, giving word 23. In 1D it is position 1 of tile 1, giving `8192 + 16 + 2 + 4 = 8214`. Thus 2D→1D must copy source word 23 to destination word 8214; 1D→2D must copy source word 8214 to destination word 23. This derivation describes candidate behaviour without reproducing proprietary instructions.

The CPU self-test checks each literal pair against its logical token and checks both directional reference outputs using unique bit patterns. It requires mismatches for an identity reference, reversed orientation, swapped dimension fields on non-square fixtures, and the unchanged designated destination that a source/destination field reversal would leave. These are CPU counterexamples, **not deliberately malformed GPU launches** or additional hardware ABI evidence. The literal pairs independently constrain the implementation against accidental self-consistency; their behavioural rationale remains subject to the experimental scope above.

## Guard and persistence limits

Each allocation has 256-word (1024-byte) guards before and after the active tensor, preserving active address alignment. Different source/destination and pre/post patterns expose a surplus cross-allocation identity copy that identical canaries could conceal. Full readbacks detect changed guarded words and changed source words. An extra launch block exercises the empirically observed count guard.

Surrounding canaries are not a memory-safety proof: they cannot detect read-only out-of-bounds accesses, writes beyond the finite surrounding allocation, or writes that restore/retain expected bytes. They do not cover all shapes, launch configurations, scheduling or kernel paths. The CPU guard control demonstrates distinct patterns, not GPU memory isolation.

This probe reads the pinned Windows DLL as data and loads only the selected GPU module into memory; it does not execute PE host code, perform neural evaluations or use model weights. It deliberately writes no weight payloads, GPU module images or proprietary disassembly to output files. **That is not a no-persistence guarantee:** core dumps are disabled and the launcher disables the CUDA compilation cache, but process memory is not locked or reliably erased; swap, temporary-memory backing and driver-managed persistence are not controlled. The machine currently uses compressed zram swap; this observation is not a guarantee about future configuration or all data handling. No system swap settings are changed.

The wider investigation already retains disassembly in ignored `research/native-linux/` files, including `helper-analysis-{6,12,14}.txt` and host-code analyses. These are outside the source-only checkpoint, are not new outputs of this probe, and must be separately audited before publication. New evidence records source hashes, dimensions, counts and numerical validation results—not proprietary instruction text or payloads.

## CPU-only verification

From the repository root:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 vr/native-tensor-probe.py self-test
```

On 09/10/2026 this passed: five non-identity known-answer pairs, ten directional word checks, 19 rejected tensor-specific negative controls, 221184 words across six bijective/round-trip shape checks, four non-identity shapes, invalid-dimension rejection and cross-allocation guard-copy rejection. This mode does not construct a CUDA driver, read a DLL or launch GPU work.
